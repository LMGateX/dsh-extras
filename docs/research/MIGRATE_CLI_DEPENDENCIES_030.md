# v0.3.0 standalone migration CLI: Cordis dependency resolution

## Scope and evidence status

- **Source baseline:** dedicated research worktree at `9d226e2`, package version `0.3.0` ([manifest](<../../package.json#L1-L10>)). Initial Git status was clean.
- **Research only:** read contributor/release/architecture/migration/acceptance contracts and the glossary; inspected source, build scripts, test code and read-only installed baseline host files. No implementation, build, package installation, migration invocation, host/browser run, real HOME/profile write, or commit was performed. This report is the only repository file written.

No local generated distributions or archives were available in this research worktree. The parent independently owns retained-release-archive checksum, install and reproduction evidence; the archive was publicly verified in the preceding release task, not freshly downloaded for this static audit. ## Finding: a runtime-only Goal ownership import escaped into offline startup

**Confirmed import chain:**

| Stage | Primary evidence |
| --- | --- |
| CLI eagerly imports the migration engine | [CLI:4-5](<../../src/migration/cli.ts#L4-L5>) |
| Engine eagerly imports discovery | [engine:8-12](<../../src/migration/engine.ts#L8-L12>) |
| Discovery eagerly imports the native Goal owner inspector | [discovery:6-8](<../../src/migration/discovery.ts#L6-L8>) |
| Native owner inspector eagerly imports runtime `Context` from `@deepseek-ai/cordis` | [native-owner:1-4](<../../src/migration/native-owner.ts#L1-L4>) |
| Runtime `Context` is needed for the root-lifetime lease check, only after checking for an actual continuation Context | [native-owner:20-26](<../../src/migration/native-owner.ts#L20-L26>) |

The CLI provides explicit profile/home/install-anchor facts and an empty loader, but **no** continuation Context ([CLI:13-19](<../../src/migration/cli.ts#L13-L19>)). The owner inspector already returns an explicit offline verification refusal when that Context is absent ([native-owner:21-22](<../../src/migration/native-owner.ts#L21-L22>)). Thus the runtime Cordis value import is unnecessary for every normal CLI call; the guard cannot prevent static dependency resolution.

`--help` is checked inside `migrationMain`, after static imports have loaded ([CLI:8-9](<../../src/migration/cli.ts#L8-L9>)). The final `.catch` handles the invocation promise, not failure to link its dependency graph ([CLI:35-37](<../../src/migration/cli.ts#L35-L37>)). This explains why a loader-level failure can bypass both help output and the CLI’s generic migration failure message.

**Inferred consequence:** plain Node launching the built CLI from a profile package without a resolvable local/ancestor Cordis package fails before parsing `--install-anchor`, even if that anchor identifies a complete matching DSH installation elsewhere. Changing cwd, passing a valid anchor, or selecting the retry/chime split cannot repair this eager import. Discovery only *calls* Goal inspection for a Goal target ([discovery:279-281](<../../src/migration/discovery.ts#L279-L281>)); conditional invocation does not make its top-level import conditional.

This is not caused by a type-only dependency: the Cordis import in [migration types:1](<../../src/migration/types.ts#L1>) is erased by compilation. The planner/validator branch uses config-only validation ([planner:1-2](<../../src/migration/planner.ts#L1-L2>), [validation:1-8](<../../src/migration/validation.ts#L1-L8>)); its reasoning-policy helper has no imports ([policy helper](<../../src/modules/compact-context/reasoning-policy.ts#L1-L76>)). The runtime value import above is the direct startup dependency found in this graph. Ordinary YAML remains an intentionally declared dependency ([engine:8](<../../src/migration/engine.ts#L8>), [generated dependencies](<../../scripts/build.mjs#L52-L53>)).

## Packaging and host-peer contract

**Confirmed:** all five distributions are generated in one loop from the same CLI and migration entrypoints. Both emitted entries bundle local code but leave `@deepseek-ai/*` and YAML external ([distribution selection](<../../scripts/distributions.mjs#L1-L8>), [build loop and entries](<../../scripts/build.mjs#L12-L24>)). Every manifest exports the migration API and installs the `dsh-extras-migrate` binary ([public entries/bin](<../../scripts/build.mjs#L42-L50>)). Exact host versions are read from the build’s anchored DSH, declared as peers, and **all** peers are optional; only Schemastery and YAML are normal runtime dependencies ([host peer list](<../../scripts/build.mjs#L9-L11>), [peer generation](<../../scripts/build.mjs#L35-L53>)). Cordis is therefore declared, but not guaranteed to be physically installed by a clean consumer. Packing uses those generated directories without rewriting imports ([pack script](<../../scripts/pack.mjs#L11-L17>)).

**Inferred breadth:** the source defect affects all five emitted CLI bundles and the public migration JavaScript entry, not just the combined CLI, unless a build optimizer or the actual released archive differs from the inspected recipe. Actual public bytes and exact import lines must be confirmed by the parent. The root plugin is a different execution contract: it deliberately imports host services and is loaded by DSH, not promised to be a host-free Node entry.

The correct contract is **an existing host installation, not a second installed host runtime**. The architecture explicitly forbids bundling a second Cordis/service registry ([architecture:27-35](<../ARCHITECTURE.md#L27-L35>)); installation docs require the matching runtime already to exist ([README:21-29](<../../README.md#L21-L29>)). The CLI is nevertheless a documented direct profile binary with explicit host anchoring ([README:45-56](<../../README.md#L45-L56>)). It must not accidentally depend on host bootstrap hooks just to start.

Read-only inspection of the installed **DSH 0.2.2-alpha.3** primary implementation corroborates the distinction:

- [DSH manifest:1-4,22-31](</home/dev/.local/lib/node_modules/@deepseek-ai/dsh/package.json#L1-L31>) declares the host and its Cordis/app-boot dependencies. The [app-boot manifest:1-4](</home/dev/.local/lib/node_modules/@deepseek-ai/dsh/node_modules/@deepseek-ai/dsh-app-boot/package.json#L1-L4>) identifies the same baseline. These are local audit citations, not paths to embed into shipped code.
- Host `routeLinked` checks declared peer names before choosing a local candidate ([native resolver:2462-2490](</home/dev/.local/lib/node_modules/@deepseek-ai/dsh/node_modules/@deepseek-ai/dsh-app-boot/lib/index.js#L2462-L2490>)). This is host loader behavior, not a Node/npm feature conferred by writing peer metadata.
- Native `resolveBundleDir` documents installation-anchor-first, then profile lookup; the anchor is an absolute **file inside the DSH app**, normally its package manifest ([native helper:1762-1779](</home/dev/.local/lib/node_modules/@deepseek-ai/dsh/node_modules/@deepseek-ai/dsh-app-boot/lib/index.js#L1762-L1779>)).
- Extras discovery already resolves app-boot through `createRequire(profile.installAnchor)` and imports its resolved file URL ([discovery:100-111](<../../src/migration/discovery.ts#L100-L111>)); native callback identity is also resolved through the anchor ([native-owner:27-32](<../../src/migration/native-owner.ts#L27-L32>)). Mutating migration uses the host’s exact anchored writer lock, not a private lock implementation ([storage:28-33](<../../src/migration/storage.ts#L28-L33>)).

Official Node documentation specifies `ESM_RESOLVE(specifier, parentURL)` and bare `PACKAGE_RESOLVE` relative to that importing module, not a later CLI flag ([resolution algorithm](<https://nodejs.org/docs/latest-v24.x/api/esm.html#resolution-algorithm-specification>)). It also states that `NODE_PATH` is not used for import specifiers ([No NODE_PATH](<https://nodejs.org/docs/latest-v24.x/api/esm.html#no-node_path>)). These explain why a separately installed host is not discovered by the CLI’s initial bare import. No claim about a specific package manager’s optional-peer behavior is needed to establish this mismatch.

## Recommended minimal safe repair (proposal, not implementation)

1. **Make the offline migration import graph Cordis-runtime-free.** Convert the native owner module’s Cordis import to types only. Retain the existing no-continuation-Context return *before any runtime Cordis acquisition*. This repairs help and offline API startup without changing profile discovery/planning, peer policy, feature implementations or host management.
2. **When an actual runtime Context exists, acquire Cordis through the explicit host installation anchor**, using the existing anchored `createRequire(...).resolve(...)` plus resolved-file-URL import pattern. Read and validate `Context.isolate` from that installed module; verify the actual supplied root has the required isolation-map shape. Failure to resolve/load/validate must return `verified:false` with a precise non-secret runtime/restart diagnostic, never proceed as though there were no startup lease. Keep the existing exact native callback, Loader-entry, actual root and registry correlation checks.
3. **Preserve all ownership semantics.** Never fabricate continuation Context in CLI mode, bypass the lease test, treat absent runtime evidence as `verified:true`, or turn every module off because Goal proof is missing. The required offline Goal limitation is explicit ([migration contract:11-13](<../MIGRATION.md#L11-L13>)); it is added only to Goal problems ([discovery:279-281](<../../src/migration/discovery.ts#L279-L281>)), and planning conflicts are per-module ([planner:30-36](<../../src/migration/planner.ts#L30-L36>)). Runtime orchestration supplies the real Context ([runtime adapter:33-45](<../../src/runtime.ts#L33-L45>)); the public API also accepts one ([host interface:9-24](<../../src/migration/types.ts#L9-L24>)).
4. **Lock the regression at the packed plain-Node seam before treating it as fixed.** Add the absent-peer stage before artifact test symlinks, keep the existing anchored-host stage, and inspect all three emitted server-side entries. A declaration-only audit or green source tests cannot establish the required repair.

A plain delayed `import("@deepseek-ai/cordis")` is **not a complete repair**: it allows the offline early return but retains the same package-relative lookup for public migration API consumers that supply an actual Context without host bootstrap hooks. Likewise, delaying the CLI engine import until after help would fix help only, not inspect/dry-run or import of the public migration API.

**Identity nuance:** audited Cordis 4.0.6-alpha.2 uses `Symbol.for("cordis.isolate")`, exposed as `Context.isolate` ([symbol definition](</home/dev/.local/lib/node_modules/@deepseek-ai/dsh/node_modules/@deepseek-ai/cordis/lib/index.js#L37-L46>), [public static](</home/dev/.local/lib/node_modules/@deepseek-ai/dsh/node_modules/@deepseek-ai/cordis/lib/index.js#L1725-L1732>), [version](</home/dev/.local/lib/node_modules/@deepseek-ai/dsh/node_modules/@deepseek-ai/cordis/package.json#L1-L4>)). Do **not** argue that every second Cordis copy necessarily changes this symbol. The no-second-runtime rule protects actual registry/service/callback ownership, and anchored acquisition avoids relying on arbitrary consumer-local classes. Existing root/callback checks must still reject a mismatched host realm.

### Alternatives and tradeoffs

| Alternative | Assessment |
| --- | --- |
| Inject only the exact host isolation-key/root-evidence accessor into migration | Strong explicit boundary with no runtime Cordis import, especially when supplied by the owning runtime. Broader interface/declaration/test change; public API callers still need an anchored safe path or clear fail-closed behavior. Not a reason to silently stop supporting existing API use. |
| Use a small pinned adapter for `Symbol.for("cordis.isolate")` | Technically supported by the inspected baseline, with no Cordis runtime import at all. Couples migration to an audited symbol/shape protocol; must document/version-check it and fail closed on unknown shape. Prefer anchored public `Context.isolate` unless avoiding all runtime acquisition is a deliberate contract decision. |
| Dynamically import a separate runtime-owner module only after the offline guard | Clean separation, but its Cordis acquisition must still be anchored. Build all distributions and examine output: bundling may move a nested static import back to top level. A real code-split runtime file must be packed and tested. |
| Make Cordis a required peer/ordinary dependency or bundle it | Reject as the primary repair: can create another runtime dependency tree or auto-install pressure and contradict the no-second-Cordis distribution contract. It also leaves an unnecessary offline dependency. |
| Require users to supply symlinks, `NODE_OPTIONS`, or bootstrap the entire host | Useful only as an explicit disposable diagnostic, not the supported minimal repair. Adds topology/bootstrap side effects, leaves help/API brittle, and `NODE_PATH` alone cannot fix ESM. |
| Catch import failures globally or remove native ownership checks | Reject: obscures actionable dependency errors or weakens fail-closed Goal safety. Missing proof must never become an admission grant. |

Any deliberate narrowing of the documented CLI/API or changing the host-peer contract requires an evidence-backed amendment before implementation ([contributor rule](<../../AGENTS.md#L11>), [completion rule](<../SPEC.md#L31-L33>)); fixing the accidental eager import should not require relaxing either contract.

## Bottom line

The source establishes an **offline/startup boundary regression**, not a missing Cordis declaration: optional host peers are appropriate for the plugin contract, but one eager runtime value import makes the standalone migration entry depend on loader wiring that it does not establish. The smallest safe correction removes that eager dependency and anchors runtime-only acquisition without weakening Goal owner verification. Public-archive reproduction and post-fix execution remain the parent’s separate evidence; no implementation or compatibility success is claimed by this report.
