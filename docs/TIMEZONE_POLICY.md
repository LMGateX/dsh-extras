# 请求上报时区覆盖：已认可需求与实施前契约

日期：2026-11-16（Asia/Shanghai）。状态：**需求已认可，文档固定；功能未实现、未发布**。

用户明确认可：请求上报时区支持覆盖，覆盖对象包括模型提示中的 `Browser time zone for this request`，不能只另加一条“有效时区”指令。此次授权仅包含文档与补充调查，不包含功能实施、生产安装、推送或发布。

## 2. 已认可的产品行为

### 2.1 请求上报时区

提供三种模式，默认不改变现有行为：

| 模式 | 本次请求实际携带的 `clientTimeZone` |
| --- | --- |
| browser：自动检测 | 浏览器检测到并经宿主规范化的 IANA 时区 |
| fixed：指定时区 | 用户选择的规范时区，例如 `Asia/Singapore` |
| host：跟随服务器 | 当前连接的 DSH 宿主进程提供并校验的时区；不是客户端猜测 |

必须覆盖实际请求字段，而非仅修改界面文案、追加相反提示或替换字符串。普通 prompt、queue、steer、人工给子 agent 发消息的入口必须一致。

### 2.2 区分检测事实与上报策略

示例：浏览器检测上海，用户指定新加坡：

```text
请求上报模式：指定时区
指定值：Asia/Singapore
浏览器检测值：Asia/Shanghai
实际请求上报：Asia/Singapore
来源：手动覆盖
```

- 保留真实检测值与覆盖来源，用于用户可见诊断；不把手动选择误记成自动检测事实。
- 模型收到的主时钟与 `Browser time zone for this request` 应一致采用本次上报值。此处标签表达客户端为本次请求选定的时区，不再只能表示自动检测结果。
- 不再额外注入“另一个有效时区”与原生主指令竞争。真实检测值可以显示在诊断界面，不必再附带一条相反的模型解释规则。
- 不修改操作系统时区、不改全局 `Intl`/`Date`、不设置全局 `TZ`、不篡改第三方工具输出。
- 用户在具体请求里明确指定的时间语义（如“纽约时间九点”）优先于默认解释时区；不把全部时间强制换算为偏好时区。

### 2.3 预期模型内容

```text
Time sampled while preparing turn 2, step 1: 2026-11-16T16:30:23+08:00[Asia/Singapore]
Browser time zone for this request: Asia/Singapore. Interpret otherwise-unqualified dates and times in this zone.
```

历史消息及已保存的历史注入不追溯改写。新策略必须影响下一次新提交进入的请求；不能被十分钟时钟节流隐藏。已经发送的 provider 请求及其自动重试保留原时区策略快照；这不限制原生重试/压缩机制依法重建请求表面。

## 3. 实现方向：一个解析模块与一个注入所有者

### 3.1 建议的最小 interface（尚非原生接口）

```ts
type RequestTimeZonePolicy =
  | { mode: 'browser' }
  | { mode: 'fixed'; timeZone: string }
  | { mode: 'host' }

// 示意：字段落点、持久化事件与权限校验须在实施前对齐原生契约。
// resolveRequestTimeZone(policy, detectedZone, hostFacts)
// -> resolved { timeZone, source, policyRevision, sampledAt, detectedTimeZone? }
//  | unavailable { reason }
```

解析模块隐藏规范化、来源、缺失值、宿主连接代次和快照选择，发送入口不各自实现策略。客户端与宿主均校验 IANA 名称；UTC 允许，别名按原生契约规范化，非法 fixed 值拒绝保存或发送，不能静默回退成浏览器/服务器值。

fixed 模式不应因浏览器检测失败而失效；检测值可以 unavailable。host 模式在未获得可靠宿主事实时不可用，不能冒充浏览器时区。宿主元数据必须归属当前连接代次，切换连接后不可沿用旧服务器值。

### 3.2 请求快照与入队

- 每次新提交捕获一个上报快照，保存检测来源与策略修订；这不授权修改现有 RPC schema，新增元数据需要显式扩展原生类型及存储契约。
- 已入队的消息保留提交时快照，不在执行时从另一个标签页的偏好重新采样；更改设置影响后续提交。
- 同轮已提交与新提议消息可能属于不同策略。不得只把新字段塞进旧的“同轮全部时区并集”而制造 `mixed`，也不能按最后到达者默默覆盖真正的多用户冲突。实施前必须定义 step 所消费的快照归属及冲突处理。
- 设置保存、运行时激活、下次请求生效应分别可见。语义/策略修订变化须越过时钟刷新节流；普通耗时与时钟刷新仍可保持原生策略。
- 一次 provider 自动重试沿用已准入的请求快照，不在每次重试重新采样或重写已入历史。

### 3.3 原生与 Extras 的职责

- 原生客户端发送 interface 应提供受支持的时区解析 seam；原生时间上下文负责选定请求的解释策略及唯一主时钟。
- Extras 可以提供编辑 UI 和配置编排，但新增设置项并不会自动接管内置发送、聊天格式化或宿主元数据。
- 原生 preset 已挂载时钟；严禁为覆盖目的再挂第二套互相矛盾的时钟。关闭/卸载后必须撤销自有 hook，不残留覆盖。
- 旧 `time-context.timeZone` 保留“显示兜底”语义，不直接改为强制覆盖；新策略使用独立配置。

## 4. 无浏览器路径：不能伪造来源

补查证明后台路径并不普遍携带 `clientTimeZone`。这些路径必须进入显式覆盖矩阵，不能以“Web 上报已改”宣称全覆盖：

| 路径 | 将来实现时的约束 |
| --- | --- |
| UI 空消息重试 | 宿主来源是 retry；须显式处理其策略快照，不把重试伪装为新的人类 user 消息 |
| goal 自动轮、job 通知 | 传播或读取明确的会话策略；无可靠来源时保留缺失/澄清，不伪造 browser 检测 |
| spawn/fork | 明确新任务与历史 seed 的策略关系；不能仅凭 fork 里存在旧时钟断言继承成功 |
| SDK/headless/ACP | 无浏览器时允许未来显式输入或明确配置来源；旧客户端不传字段仍保持兼容 |
| compaction/恢复/模型切换 | 保留结构化策略及来源；不能只依赖摘要模型记住一段时间文本 |
| 自动 provider 重试 | 复用同一步准入快照，不重新注入、不改变已发送请求语义 |
| 定时提醒投递 | 规则 occurrence 与请求默认解释策略分开；不得把任务时区伪称浏览器检测值 |

**待实施前决策**：profile 默认与客户端/会话覆盖的准确存储与权限范围；后台读取“最后一次已准入快照”还是显式会话策略；fork/spawn 的继承与清除规则；多来源同轮冲突的原生事件形式。以上不冒称已获用户逐项选择，必须在写功能代码前确定，不能靠隐式 last-writer-wins 补齐。

## 5. 工具与显示的保留边界

- **定时任务**：已有 `TZID`/`time_zone`、UTC occurrence、next-run 与历史执行语义不改。新默认时区可帮助解释创建请求，但不得重排已有任务。
- **shell / PowerShell / terminal**：程序的 Date、系统时区、继承 `TZ` 是执行环境事实。请求偏好不能偷偷变成全局进程环境覆盖；确有工具级需求应另行显式配置。
- **PTC**：空 `process.env` 不等于 Date/Intl 已按请求偏好执行。需独立验证运行时，不承诺随 clientTimeZone 改变。
- **工具结果 / MCP / web / Office**：保留原数据的 epoch、UTC、offset、文档日期与外部来源。不得扫描结果文本批量替换时区；不明来源保持不明。
- **耗时/超时/退避/去抖**：按 duration/epoch 计算，不受时区偏好影响。
- **聊天界面**：格式化、今天/昨天、日界线、午夜刷新需统一支持选定显示时区；作为后续独立阶段，不把请求覆盖说成 UI 已同步。
- **任务编辑器**：当前新草稿独立使用浏览器默认值；若后续联动，只影响新建默认值，保留已选草稿、显式高级规则与旧任务。
- **Extras Chime 勿扰时段**：当前按浏览器本地时钟判断，首版保持原行为。若要跟随请求时区必须新增明确选择，不隐式改变夜间响铃时段。

## 7. 阶段与未授权事项

1. 本次：固定需求、调查所有入口、运行现有行为的隔离特征回放；不实现功能。
2. 实施前：补齐第 4 节决策，确认原生 seam 或严格版本限定的 adapter；不能默认以修改 node_modules 交付。
3. 首版：请求上报覆盖、来源展示、主时钟一致性与明确的后台覆盖范围；不以只支持手动 Web prompt 冒称全入口。
4. 后续独立阶段：聊天显示时区与可选任务新建默认值联动；Chime 勿扰/进程 TZ 不自动加入。
